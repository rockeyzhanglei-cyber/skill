# 工作流程详细指南

## 七阶段渐进式工作流

本技能采用七阶段渐进式工作流，每个阶段独立可控：

```
阶段0: TFS需求获取 → 阶段0.5: Wiki内容获取 → 阶段0.6: 创建AI分析任务 → 阶段1: 需求评估 → 阶段2: 需求补充 → 阶段3: 需求PRD设计 → 阶段4: 原型设计 → 阶段5: TFS需求分析 → 阶段6: TFS上传 → 阶段6.5: 完成AI分析任务
```

> **注意**：
> - 阶段0（TFS 需求获取）为可选步骤。用户可直接提供需求文本，跳过此阶段。
> - 阶段0.5（Wiki 内容获取）为可选步骤。当需求描述中包含 Wiki URL 时自动触发。
> - 阶段3完成后建议先审核功能需求文档，确认无误后再进入原型设计
> - **阶段6（TFS上传）为可选步骤**，用户可选择是否将需求分析上传到TFS

### 输出文件目录结构

所有过程文件按需求号分目录存储，便于管理和追溯：

- **从 TFS 获取的需求**：使用工作项 ID 作为目录名和文件名前缀
  ```
  过程文件/1445554/1445554_需求设计_01_需求合理性评估报告.md
  过程文件/1445554/1445554_需求设计_02_功能需求.md
  过程文件/1445554/1445554_需求设计_03_原型说明.md
  过程文件/1445554/1445554_需求设计_04_TFS需求分析.md
  ```

- **手动输入的需求**：使用年月日作为目录名和文件名前缀（格式：YYYYMMDD）
  ```
  过程文件/20260228/20260228_需求设计_01_需求合理性评估报告.md
  过程文件/20260228/20260228_需求设计_02_功能需求.md
  过程文件/20260228/20260228_需求设计_03_原型说明.md
  过程文件/20260228/20260228_需求设计_04_TFS需求分析.md
  ```

## 阶段0: TFS 需求获取（可选）

### 触发条件
用户提供 TFS 工作项 ID

### 输入格式
```
工作项 ID: [数字编号]
项目: [项目名称，可选]
```

示例：
```
工作项 ID: 12345
项目: WiNEX-Outpatient
```

### 处理流程
1. 检查 TFS 配置文件是否存在（按优先级）：
   - **优先级1：全局配置** - `~/.claude/skills/tfs2018-integration/config/tfs-config.json`（首选）
   - **优先级2：项目级配置** - `config/tfs-config.json`（备选）
2. 检查 TFS 依赖包是否安装：
   ```bash
   cd ~/.claude/skills/tfs2018-integration && npm list azure-devops-node-api
   ```
3. 如果依赖缺失，提示安装：
   ```bash
   cd ~/.claude/skills/tfs2018-integration && npm install
   ```
4. 使用 TFS 查询工具获取工作项：
   ```bash
   node ~/.claude/skills/tfs2018-integration/query-wi.mjs [工作项ID]
   ```
5. 提取关键字段：标题、描述、状态、优先级等
6. **必须使用 AskUserQuestion 弹框确认需求**：
   - 展示需求信息
   - 提问："是否确认以上需求理解正确并进入需求评估阶段？"
   - 选项：
     - "确认，进入需求评估"
     - "需要修改需求内容"
     - "手动输入需求"
7. 用户确认后，**记录工作项 ID**（用于后续创建目录）

### TFS 配置（仅需配置一次）

**全局配置**（推荐）
- 位置：`~/.claude/skills/tfs2018-integration/config/tfs-config.json`（用户主目录）
- 优点：配置一次，所有项目共享使用
- PAT 有效期：通常几个月到一年

```json
{
  "serverUrl": "http://tfs2018-web.winning.com.cn:8080/tfs/WINNING-6.0",
  "pat": "your-personal-access-token-here"
}
```

**配置路径示例**：
- Windows: `C:\Users\你的用户名\.claude\tfs-config.json`
- macOS/Linux: `~/.claude/skills/tfs2018-integration/config/tfs-config.json`

**项目级配置**（可选）
- 位置：项目根目录 `config/tfs-config.json`
- 用途：仅在全局配置不存在时，或特殊项目需要不同配置时使用

**获取 PAT Token**：
1. 登录 TFS: http://tfs2018-web.winning.com.cn:8080/tfs/
2. 用户头像 → 安全 → +添加 → 个人访问令牌
3. 选择权限：工作项(读取、管理)、代码(读取)
4. 复制生成的令牌并保存到配置文件

## 阶段0.5: Wiki 内容获取（可选）

### 触发条件

需求内容（TFS 工作项描述或用户手动输入）中包含 Wiki URL。

### Wiki URL 识别规则

自动检测以下任一模式的 URL：
- `pageId=数字`（如 `pageId=12345`）
- `/pages/数字`（如 `/pages/12345`）
- `/display/空间Key/`（如 `/display/DEV/页面标题`）
- 公司 Wiki 域名（如 `wiki.company.com`）

**正则表达式**：
```regex
(pageId=\d+|/pages/\d+|/display/\w+/|wiki\.company\.com)
```

### 处理流程

#### 步骤1: 提取 Wiki URL

从需求描述中使用正则匹配提取所有 Wiki URL，去重后得到 URL 列表。

```
发现 Wiki 引用：
- http://wiki.company.com/pages/viewpage.action?pageId=12345
- http://wiki.company.com/display/DEV/设计规范
```

#### 步骤2: 获取 Wiki 页面内容

使用 wiki-mcp 工具获取页面内容：

```javascript
mcp__wiki-mcp__wiki_get_page({
  pageIdOrUrl: "http://wiki.company.com/pages/viewpage.action?pageId=12345",
  embedImages: false  // 不嵌入图片，节省 token
})
```

**返回字段**：
| 字段 | 说明 |
|------|------|
| `id` | 页面 ID |
| `title` | 页面标题 |
| `spaceKey` | 空间 Key |
| `spaceName` | 空间名称 |
| `content` | Markdown 格式的页面内容 |
| `url` | 页面 URL |
| `lastUpdated` | 最后更新时间 |

#### 步骤3: 整合到分析上下文

将获取的 Wiki 内容作为辅助材料整合到后续分析流程中：

| 后续阶段 | Wiki 内容用途 |
|----------|--------------|
| **阶段1（需求评估）** | 了解业务背景、现有方案、设计规范 |
| **阶段3（功能设计）** | 参考已有功能文档、接口规范 |
| **阶段4（原型设计）** | 遵循 UI/UX 设计规范 |
| **阶段5（TFS 分析）** | 补充技术细节、实现方案 |

#### 步骤4: 在文档中引用 Wiki 来源

在生成的评估报告和需求文档中，添加 Wiki 引用说明：

```markdown
## 参考文档
- [Wiki 页面标题](Wiki URL) - 获取时间：2024-01-01
```

### 常见 Wiki 内容类型

| Wiki 类型 | 分析用途 |
|-----------|----------|
| 设计规范 | 原型设计时遵循 UI/UX 规范 |
| 功能文档 | 参考已有功能设计模式 |
| 技术方案 | 了解技术实现细节和约束 |
| 业务流程 | 理解业务背景和流程 |

### 输出

**Wiki 内容上下文**：获取的 Wiki 页面内容将作为后续阶段分析的参考材料。

### 错误处理

**Wiki URL 无法访问**：
```
⚠️ Wiki 页面获取失败

URL: http://wiki.company.com/pages/viewpage.action?pageId=12345
原因: 页面不存在或无访问权限

将继续使用已有需求信息进行分析。
```

**wiki-mcp 未配置**：
```
⚠️ wiki-mcp 未配置，跳过 Wiki 内容获取

将继续使用已有需求信息进行分析。
```

### 阶段完成输出

**获取成功**：
```
✅ 阶段0.5：Wiki 内容获取已完成

获取的 Wiki 页面：
- [设计规范文档] - http://wiki.company.com/pages/viewpage.action?pageId=12345
  最后更新：2024-01-15

Wiki 内容将作为后续分析的参考材料。

下一步：进入阶段1（需求评估）
```

**无 Wiki URL**：
```
未检测到 Wiki URL，跳过此阶段。

下一步：进入阶段1（需求评估）
```

## 阶段1: 需求合理性评估

### 触发条件
用户提供客户需求（通过 TFS 获取或手动输入）

### 输入方式

**方式1: TFS 工作项 ID（推荐）**
```
工作项 ID: 12345
```

**方式2: 手动输入**
```
①背景：[业务背景说明]
②需求：[具体需求描述]
```

### 处理流程
1. 解析需求背景和业务场景
2. 识别需求中的关键信息和缺失信息
3. 使用五维评估框架进行量化评估
4. 根据综合评分确定需求分级（S/A/B/C）
5. 判断需求本质（真实需求/伪需求/设计漏洞）
6. 生成标准化评估报告

### 五维评估框架

本阶段采用五维评估框架（依据《需求管理办法V1.1》），对需求进行标准化量化评估：

| 评估维度 | 满分 | 评估要点 |
|----------|------|----------|
| **需求合理性** | 25分 | 业务逻辑自洽性、技术实现可行性、需求边界清晰度、业务场景真实性、合规性 |
| **需求必要性** | 25分 | 解决痛点程度、使用频率预期、用户覆盖范围、业务价值贡献、紧迫程度 |
| **现有功能兼容性** | 25分 | 功能重复度、系统一致性、数据兼容性、流程协调性、维护成本影响 |
| **新功能完整性** | 25分 | 功能点覆盖、输入输出明确、异常处理考虑、业务闭环性、扩展性考虑 |
| **业务相关性** | 25分 | 战略契合度、业务条线关联、跨条线影响、数据关联度、流程关联度 |
| **总计** | **125分** | 综合评分 |

### 需求分级标准

根据五维评估的综合评分，确定需求分级：

| 等级 | 分数范围 | 处理方式 |
|------|----------|----------|
| **S级** | ≥100分 | 重要且紧急，启用快速通道处理 |
| **A级** | 80-99分 | 合理且必要，按正常流程处理 |
| **B级** | 60-79分 | 存在疑问，需要澄清后处理 |
| **C级** | <60分 | 不合理或不必要，建议驳回 |

### 需求本质分析

通过三个核心问题判断需求本质：

1. **客户是否真正理解自己的需求？**
2. **提出的解决方案是否真的能解决问题？**
3. **是否是现有产品的问题，而非需求本身的问题？**

根据回答判定：
- **真实需求**：客户明确表述的问题，需要新增或修改功能
- **伪需求**：客户误解自己的真实诉求，提出的方案无法解决问题
- **设计漏洞**：现有产品设计问题，应优化现有产品而非新增功能

### 复杂度预判

| 复杂度 | 说明 |
|--------|------|
| **简单** | 单一功能，逻辑清晰，无复杂交互 |
| **复杂** | 多功能联动，业务逻辑复杂，涉及多系统集成 |
| **无法判断** | 缺少关键技术或业务信息，需要研发评估 |

### 输出

**步骤1: 创建需求号目录**
```bash
# 必须先创建需求号子目录，再生成文件
mkdir -p "过程文件/[需求号]"
```

**目录结构示例**：
- TFS 工作项 ID（如：1445554）
  ```
  过程文件/
  └── 1445554/
      ├── 1445554_需求设计_01_需求合理性评估报告.md
      ├── 1445554_需求设计_02_功能需求.md
      ├── 1445554_需求设计_03_原型说明.md
      └── 1445554_需求设计_04_TFS需求分析.md
  ```

- 手动输入需求时使用年月日（如：20260228）
  ```
  过程文件/
  └── 20260228/
      ├── 20260228_需求设计_01_需求合理性评估报告.md
      ├── 20260228_需求设计_02_功能需求.md
      ├── 20260228_需求设计_03_原型说明.md
      └── 20260228_需求设计_04_TFS需求分析.md
  ```

**步骤2: 在需求号目录下生成评估报告文件**

**重要**：
1. **必须先创建需求号子目录 `过程文件/[需求号]/`，再在此目录下生成文件**
2. **文件名必须包含需求号前缀**，如：`1445554_[需求号]_需求设计_01_需求合理性评估报告.md` 或 `20260228_需求设计_01_...`
3. 必须严格按照 [templates.md](templates.md#需求合理性评估报告) 中的模板结构生成
   - 不得随意增删章节或改变结构
   - 不得添加模板之外的内容、章节或说明
   - 不得添加额外的标题、签名、日期等元信息

**正确示例**：
```bash
# ✅ 正确：创建子目录后，在子目录下生成带前缀的文件
mkdir -p "过程文件/1445554"
# 在 过程文件/1445554/ 目录下生成：1445554_需求设计_01_需求合理性评估报告.md
```

**模板结构**（采用五维评估框架）：
- 一、需求概述
- 二、需求解读（业务场景理解、核心诉求识别、功能识别）
- 三、五维评估（需求合理性、需求必要性、现有功能兼容性、新功能完整性、业务相关性）
- 四、需求分级（S/A/B/C 等级、复杂度预判、需求本质分析）
- 五、完整性评估（已明确信息、待澄清问题）
- 六、初步建议
- 七、下一步行动

**待澄清问题交互规则**：
- **问题数量 ≤ 10**：使用 AskUserQuestion 弹框对话模式
- **问题数量 > 10**：输出所有问题列表，等待用户统一回复

### 阶段完成输出

**按产品经理最佳实践的流程处理**：

根据五维评估的综合评分和待澄清问题情况，按照产品经理最佳实践选择处理流程。

**最佳实践说明**：
- 基于医疗软件行业成熟经验
- 综合考虑需求合理性、业务价值、实现可行性等因素
- 主动补充行业最佳实践，减少与客户反复确认的次数

**处理选项**：

| 选项 | 适用场景 | 说明 |

### Markdown 转 HTML 转换规则

**自动转换功能**：

脚本会自动执行以下转换：

**标题转换**：
- `# 一级标题` → `<h1>`（带蓝色底边框）
- `## 二级标题` → `<h2>`（带灰色底边框）
- `### 三级标题` → `<h3>`（蓝色）
- `#### 四级标题` → `<h4>`（深灰色）
- `##### 五级标题` → `<h5>`（浅灰色）
- `###### 六级标题` → `<h6>`（浅灰色）

**表格转换**：
- Markdown 表格 → HTML 表格（带样式）
- 表头：浅灰背景 `#F5F7FA`，加粗
- 斑马纹：偶数行浅灰背景
- 悬停效果：鼠标悬停行变浅蓝色
- 边框：淡灰色 `#DCDFE6`

**列表转换**：
- 无序列表 → `<ul>`
- 有序列表 → `<ol>`
- 列表项：适当上下间距

**文本格式**：
- 加粗 `**text**` → `<strong>`（深色加粗）
- 斜体 `*text*` → `<em>`（灰色斜体）
- 行内代码 `` `code` `` → `<code>`（浅灰背景，橙色文字）
- 代码块 → `<pre><code>`（深色背景，语法高亮色）

**链接转换**：
- `[文本](URL)` → `<a>`（蓝色链接，悬停下划线）

**HTML 样式特性**：

转换后的 HTML 包含完整样式：

```css
- 字体：微软雅黑、Arial
- 行高：1.8
- 标题间距：上下 24px/16px
- 表格：完整样式、斑马纹、悬停效果
```

## 实用工具

### MoSCoW 优先级排序

| 优先级 | 名称 | 说明 |
|--------|------|------|
| **P0** | Must have | 必须有的功能，否则产品不可用 |
| **P1** | Should have | 重要但不是紧急的功能 |
| **P2** | Could have | 锦上添花的功能 |
| **P3** | Won't have | 本期不做的功能 |

### 用户故事格式

```
作为[用户角色]，我希望[目标]，以便[价值/原因]

验收标准：
- [标准1]
- [标准2]
```
