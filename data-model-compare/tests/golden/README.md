# Golden 基线（端到端回归守卫）

本目录存放**真实数据端到端**的比对基线，供 `scripts/regression_check.py` 对比使用。

与 `tests/test_baseline.yaml`（单元级，27 条手工用例）**互补，用途不同**：

| 文件 | 守卫层级 | 覆盖面 |
|------|---------|--------|
| `../test_baseline.yaml` | 单元级 | `test_cases.yaml` 的 27 条手工用例，覆盖规则点 |
| 本目录 `*.json` | 端到端 | 真实全量数据的每个字段判定（V6.0 任务 5349 个） |

## 为什么需要两套

单元测试只有 27 条用例，而真实任务有 5000+ 字段判定。拆分
`standard_comparator.py`、重构 matcher 这类改动，**单元测试全绿不等于行为没变**。
只有端到端字段级指纹比对能证明「行为零变化」。

## 基线内容

每个基线文件记录：

- `scale` — 源/目标的表数、字段数（检测解析变化）
- `counts` — matched/modified/new_fields/new_tables 总数及各匹配类型分布
- `self_validation` — leak / suspect / 准确率
- `field_rows` + `field_rows_sha256` — **字段级指纹**

指纹行格式：
```
{判定}|{目标表}.{目标字段}|{匹配类型}|{源表}.{源字段}|{条件显示}
```

做到字段级（而非只比总数）的原因：可能出现「matched 总数不变，但某字段从
`synonym` 漂移成 `keyword`」这类静默变化，纯计数检测不出来。

## 常用命令

```bash
# 回归检查（只读，不覆盖任何产物）
python scripts/regression_check.py --task-dir "<任务目录>"

# 更新基线（人工确认当前结果正确后再执行！）
python scripts/regression_check.py --task-dir "<任务目录>" --update-baseline

# 调整差异明细显示条数
python scripts/regression_check.py --task-dir "<任务目录>" --show-diff 30
```

退出码：`0` = 无回归 / `1` = 检出回归 / `2` = 参数或文件错误

## 维护纪律

1. **不要随手更新基线**。基线的作用是"证明改动没改变行为"，
   只有人工确认新结果**确实更正确**时才用 `--update-baseline` 推进。
2. 更新基线时，在提交信息里说明：为什么结果变了、人工核验的依据。
3. 改动匹配逻辑（拆分/重构/调规则）前后各跑一次，确认差异符合预期。
