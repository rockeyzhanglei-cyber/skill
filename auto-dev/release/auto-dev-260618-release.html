📐 里程碑一：OpenSpec 规格闸门 核心特性

从"AI 直接开发"到"先规格、再确认、后开发"

v3.0 引入 OpenSpec 作为规格闸门，在 PM 分析前先生成结构化需求资产：
proposal.md（需求提案）→ design.md（技术设计）→ tasks.md（任务分解）

产物采用双路径策略：项目目录（用户可见可编辑）+ DOCS_DIR（流水线归档），确保用户始终拥有最终审阅权。

用户确认闸门 人工介入

Spec 生成后，流水线自动暂停，展示文档摘要并等待用户确认。
支持多轮对话修改：用户提出修改意见 → AI 修改文档 → 再次展示变更摘要 → 再次确认。
只有用户输入"继续"后，流水线才同步文档并进入 PM 分析阶段。

确认标记写入 .spec-confirmed，PM 阶段前置检查此标记，未确认不启动。

⚡ 里程碑二：Superpowers 执行纪律 核心特性

编码和校验阶段引入 Superpowers skill 驱动

v2.x 的编码和校验阶段依赖子代理自行推理执行流程。v3.0 改为子代理内部调用 Superpowers skill：

编码阶段：调用 test-driven-development skill → TDD 流程（先写测试再实现）+ 系统化调试 + 自查验证
校验阶段：调用 verification-before-completion skill → 功能覆盖检查 + 逻辑正确性 + 代码质量 + OpenSpec 覆盖检查

约束由 skill 内部管理，子代理只需提供路径参数，执行纪律从"提示词约束"升级为"skill 流程驱动"。

Preflight 强制检测 — 流水线启动前检测 Superpowers 关键技能文件是否存在（TDD / systematic-debugging / code-review / verification），缺失则立即终止 关键
约束解耦 — Code/Verify 子代理不再注入 constraints-code，改由 skill 内部约束，职责更清晰
流程标准化 — 编码和校验不再依赖 AI 自由发挥，skill 提供确定性的执行步骤和质量门禁
📊 里程碑三：使用埋点统计 核心特性

追踪谁在使用 Auto-Dev，量化推广情况

新增使用埋点，记录每次 Auto-Dev 流水线的触发者信息，支持统计：
- 谁在用：触发流水线的用户身份
- 用了多少次：按用户维度的使用频率
- 使用结果：成功 / 跳过 / 失败分布

为后续推广和效能分析提供数据支撑。

用户维度统计 — 每次流水线触发时上报当前用户信息，汇总可查看各团队成员的 Auto-Dev 使用情况 NEW
使用频次追踪 — 按日/周/月维度统计触发次数，了解工具采纳趋势
静默上报 — 埋点数据自动采集，不打断流水线执行，不影响用户体验
🔄 全新流水线架构 v3.0
主代理（编排器）
├─ Preflight: 环境检测（OpenSpec + Superpowers）
├─ Step 0: 准备（脚本 + MCP + WinMetrics 初始化）
├─ Step 0.5: Spec 规格生成（OpenSpec 子代理）
├─ Step 0.5.4: 用户确认闸门（暂停 → 多轮修改 → 确认）
├─ Step 1: PM 分析（消费 OpenSpec 产物）
├─ Step 2: 代码开发（Superpowers TDD skill）
├─ Step 3: 需求校验（Superpowers verification skill）
├─ Step 3.5: 单元测试（可选）
├─ Step 4: 提交 + PR
├─ Step 5: 构建
├─ Step 6: 部署
└─ Step 7: 报告 + WinMetrics 终态

🎯 v2.x → v3.0 核心变化总结 对比
需求理解 — 从"AI 直接读工作项描述"升级为"OpenSpec 生成结构化规格 → 用户确认 → PM 消费规格"，增加人工审阅环节
编码纪律 — 从"提示词约束子代理自由发挥"升级为"Superpowers skill 驱动 TDD 流程"，执行步骤确定性
可观测性 — 新增使用埋点，追踪谁在用、用了多少次，为工具推广提供数据依据
人机协作 — 流水线不再完全黑盒，Spec 阶段提供透明的文档审阅和修改机会，用户掌握最终决定权
